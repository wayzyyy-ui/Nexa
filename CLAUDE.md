# NEXA Hub: правила проекта

Дипломный проект. NEXA Hub — приложение-хаб, которое объединяет обычные устройства пользователя (телефон, ноутбук, часы, наушники, ТВ) в одну систему. Данные в нём только настоящие: выдуманных устройств, файлов и переключателей нет (демо-режим убран по решению автора) — гость видит пустые разделы с подсказками.

Автор — дизайнер, а не программист. Объясняй правки простыми словами, без жаргона.

## Стек и запуск

- React 19 + Vite, деплой на Vercel.
- Код разложен по модулям (см. «Структура кода»): `src/App.jsx` — только корневой компонент `NexaApp` (состояние, навигация, связь, уведомления), экраны — `src/screens/`, общие элементы — `src/ui/`, логика без интерфейса — `src/lib/`. Стили inline плюс один общий блок `<style>` (`src/ui/appStyles.js`).
- `api/chat.js` — серверная функция Vercel для ИИ-ассистента (сейчас Gemini через `@google/genai`). Модель — псевдоним `gemini-flash-lite-latest` (Google сам переводит его на новые модели). Обдумывание перед ответом выключаем по очереди: `thinkingLevel: "minimal"` (Gemini 3) → `thinkingBudget: 0` (старые) → без настройки (`THINKING_TRIES`): новые модели отклоняют чужую настройку ошибкой 400 «invalid argument», так ассистент однажды перестал отвечать целиком.
- Локально проект запускается командой `vercel dev` (http://localhost:3000). `npm run dev` поднимет только фронт, без `/api/chat`.
- Продакшен: https://nexaru-ecosystem.vercel.app

## Android-приложение (Capacitor)

- Папка `android/` — проект для Android Studio, `capacitor.config.json` — имя «NEXA» и id `ru.nexalink.app`.
- Сборка: `npm run build:android` (сайт с настройками из `.env.android` + копирование в `android/`), затем `npm run open:android`. Firebase (push) — `android/app/google-services.json`, только на этом компьютере (в .gitignore).
- Адрес ассистента в приложении — `VITE_API_BASE` в `.env.android` (файл в git, секретов в нём нет). На сайте адрес остаётся `/api/chat`.
- «Потяните, чтобы обновить» — только в приложении (`usePullToRefresh` + `PullIndicator`): страница прокручена до верха, тянем вниз больше 64 px → облако аккаунта, погода (событие `nexa-refresh`) и проверка обновления. Внутри окон, полей и `.nx-scroll` жест не срабатывает.
- Всё, что нужно только приложению, — в `src/native.js` (на сайте ничего не делает). Кнопка «Назад» Android — в NexaApp: закрывает окно (через Esc), потом экран устройства, потом предыдущий раздел, на Главной сворачивает.
- Отступы под вырез и системную полосу: в CSS использовать `var(--sat)` и `var(--sab)`, а не `env(safe-area-inset-*)` напрямую.
- Новые окна и меню должны иметь `role="dialog"` / `role="menu"` и закрываться по Esc — тогда кнопка «Назад» закроет и их.
- Иконка приложения: исходник `assets/logo_android.svg` (из Figma, с тенями и режимом смешивания — из него только иконки сайта `public/icons/` и `assets/icon-only.png`). Для Android — чистый логотип `assets/logo_splash.svg` (те же грани, плоские цвета с прозрачностью, без теней и размытия):
  - значок на рабочем столе — вектор `res/drawable/ic_launcher_foreground_vector.xml` (108dp, логотип в круге 66dp) на фоне `@color/nexaBg` (`mipmap-anydpi-v26/ic_launcher*.xml`);
  - заставка Android 12+ — вектор `res/drawable/splash_icon.xml` (`windowSplashScreenAnimatedIcon` в `values/styles.xml`): 288dp без подложки, логотип в видимом круге 192dp. Раньше Android растягивал в заставку PNG значка 192px — отсюда «мыло»;
  - старые заставки (Android 11 и ниже) — `res/drawable*/splash.png` и `assets/splash*.png` (2732), отрисованы из `logo_splash.svg` в точном размере, логотип — четверть короткой стороны;
  - `npx capacitor-assets generate` больше НЕ запускать: он перезапишет векторные значки картинками.
- Запуск приложения бесшовный: поверх интерфейса сразу лежит `#nx-boot` (`mountBootLogo` в `src/native.js`) — тот же логотип, того же размера (288×288, масштаб 0.1727) и в той же точке, что на заставке. `startIntro` убирает заставку, потом грани чуть разъезжаются и тают (только прозрачность и сдвиг SVG), интерфейс проявляется (прозрачность + сдвиг). Меняешь логотип — меняй одинаково `logo_splash.svg`, `splash_icon.xml`, `ic_launcher_foreground_vector.xml` и `BOOT_FACETS` в `native.js`.
- Сайт раздаёт приложение файлом `public/nexa.apk` (блок установки: баннер наверху мобильной Главной — `InstallBanner`: кто не качал APK — «Приложение NEXA · Быстрее и удобнее, чем в браузере», кто качал старую версию — «Вышла NEXA … · Обновить» (`SiteUpdateBanner`); группа «Приложение» в Настройках — `InstallSettings`). После новой сборки APK скопировать его туда заново. Команда `build:android` сама убирает `nexa.apk` из копии сайта внутри приложения, чтобы APK не попадал сам в себя.
- Обновления приложения:
  - `public/version.json` (пишет `npm run copy:apk`, скрипт `scripts/copy-apk.mjs`): `version`, `versionCode`, `minVersionCode`, `apkUrl` (ссылка с номером версии `/nexa.apk?v=909` — телефон не возьмёт старый файл из кэша), `url` (`/nexa.apk`, для приложений до 0.9.9), `size`, `sha256`, `signer` (SHA-256 сертификата подписи — по `apksigner verify --print-certs`), `notes` (что нового — строки `- …` из `release-notes.md`, до 12). Версию скрипт берёт из `output-metadata.json`, который Gradle кладёт рядом с APK, — номер в version.json всегда равен номеру внутри APK. versionCode считает `android/app/build.gradle` из `"version"` в package.json (0.9.9 → 909). Повторный запуск на той же версии не поднимает minVersionCode.
  - Проверка — `checkForUpdate({ force })` в `src/native.js`: при запуске и при возврате в приложение (`resume`), сайт спрашивается не чаще раза в 6 часов, между проверками — последний ответ (`nexa-update-cache`); «потяните, чтобы обновить» и «Проверить» в Настройках — сразу. Установленная версия — `App.getInfo().build` (Capacitor App).
  - Показ: `UpdateCard` (версия, размер, «что нового», «Обновить», «Позже») — плашкой на Главной и группой «Обновление» в Настройках (там же «Установлена последняя версия · NEXA X · Проверено в …» и «Проверить»; версия — от Android). «Позже» прячет плашку на Главной для этой версии (`nexa-update-later`), в Настройках блок остаётся. Обязательное обновление (версия старше `minVersionCode`) — `ForceUpdateScreen` без «Позже», с той же установкой изнутри.
  - Установка изнутри — `NexaUpdatePlugin.java` + общий ход `updState` / `updStart` в `src/lib/updates.js` (`UpdateActions` — `src/ui/install.jsx`): сверить ключ подписи (`signer`; другой ключ — честно «поверх не встанет, удалите и поставьте заново» и «Скачать в браузере»), скачать в `cache/updates/nexa-update.apk` (только https, прогресс, «Отменить», ошибка сети — «Повторить»), сверить размер и SHA-256, проверить право «Установка неизвестных приложений» (`canRequestPackageInstalls`; нет — экран настроек, после возврата в NEXA установка продолжается сама), открыть системный установщик через FileProvider (`file_paths.xml` — `cache-path updates/`, разрешение `REQUEST_INSTALL_PACKAGES`). Тихой установки нет: Android всегда спрашивает «Установить?», так и написано; ещё может спросить Google Play Protect — подсказка «Подробнее» → «Установить без проверки». Скачанный файл удаляется при следующем запуске (`updateCleanup`). На сайте — прежняя кнопка «Скачать APK» (`ApkButton`, `SiteUpdateBanner`).
- Подпись: `android/keystore.properties` (в git не попадает, образец — `android/keystore.properties.example`; ключ `*.jks` тоже вне git). Есть файл — `npm run release:android` собирает подписанный release (`assembleRelease`), нет — debug, как раньше (`~/.android/debug.keystore`). Обновление встаёт поверх, только если APK подписан тем же ключом, что установленное приложение: при смене ключа (debug → release) все установленные приложения один раз придётся удалить и поставить заново — copy:apk громко предупреждает, приложение показывает «поверх не встанет».
- Выпуск новой версии по шагам:
  1. поднять `"version"` в package.json и `VERSION` в `src/version.js` (0.9.8 → 0.9.9; versionCode 909 Gradle посчитает сам);
  2. вписать пункты «что нового» в `release-notes.md` (строки `- …`);
  3. `npm run release:android` — сайт для приложения → `android/`, сборка APK (release с ключом или debug), затем сам вызывает `npm run copy:apk` → `public/nexa.apk` и `public/version.json`. Флаги: `-- --hard` — закрыть все старые версии сразу, `-- --soft` — оставить прежнюю минимальную. Если APK собирали в Android Studio — после сборки отдельно `npm run copy:apk`;
  4. проверить вывод: версия, SHA-256, ключ (тот же, что в прошлый раз), число пунктов «что нового»; в `android/app/src/main/assets` не должно быть тестовых адресов;
  5. коммит (package.json, src/version.js, src/screens/About.jsx (`ABOUT_UPDATES`), release-notes.md, public/nexa.apk, public/version.json и код), пушит автор;
  6. деплой сайта (Vercel после пуша) — установленные приложения увидят обновление при следующей проверке (запуск / возврат, не чаще раза в 6 часов; «Проверить» в Настройках — сразу).
  Минимальная версия: старше неё — экран «Обновите приложение» (закрыть нельзя, «Назад» сворачивает); от неё до новой — плашка с «Позже». По умолчанию минимальная — предыдущий выпуск. Без интернета проверка не срабатывает. Установка изнутри работает в приложениях от 0.9.9; старые обновляются как раньше — через браузер (поле `url`).
- Установка на экран «Домой» (iPhone): `public/manifest.webmanifest`, иконки в `public/icons/`, мета-теги в `index.html`. На Android manifest не подключается (маленький скрипт в `index.html`), чтобы Chrome не предлагал поставить сайт как веб-приложение: на Android NEXA ставится только APK. Service worker в проекте нет и не нужен.
- Виджеты рабочего стола — нативные (Java + XML), папка `android/app/src/main/java/ru/nexalink/app/widgets/`:
  - «NEXA · Расписание» (`ScheduleWidget`, 4 × 2): до трёх ближайших дел на сегодня (время и название), «ещё N», «Сегодня свободно» / «На сегодня дел больше нет» / «Откройте NEXA…» (расписание ещё не приходило). Нажатие — раздел «Сегодня». Прошедшие дела убирает сам: будильник без точного времени (`AlarmManager.set`) на минуту после ближайшего дела и на полночь; ещё `updatePeriodMillis` 30 мин и смена времени/часового пояса.
  - «NEXA · Погода» (`WeatherWidget`, 2 × 2 и растягивается до 4 × 2): город, температура, состояние, минимум/максимум на день, «Обновлено в …». Раскладки `widget_weather_small` / `widget_weather_wide` (Android 12+ выбирает сам по размеру, ниже — по ширине). Нажатие — Главная.
  - Данные — SharedPreferences `nexa_widgets` (`WidgetStore`), поэтому виджеты работают при закрытом приложении. Пишет их плагин `NexaWidgetsPlugin` (регистрируется в MainActivity): `setSchedule({ items })`, `setCity({ city, lat, lon, api })`, `refresh()`, событие `openTab` { tab } (нажатие на виджет; при холодном запуске событие ждёт подписчика). Веб-часть — `src/native.js`: `widgetsSetSchedule` (то же `nexa-schedule`, что на «Сегодня»: только сегодня и дальше, без описаний, одинаковое не шлём), `widgetsSetCity(c)` (город, выбранный вручную, — название и координаты, плюс адрес сервера `API_BASE`; нет — Казань), `widgetsFlush` (уход в фон), `onWidgetTab`. В NexaApp: при запуске и при каждом изменении расписания, при уходе в фон; город — при запуске и в `pick` карточки погоды.
  - Погода — `WeatherWorker` (WorkManager `androidx.work:work-runtime`): периодически «раз в 30 минут» (просьба к системе — Doze и экономия заряда могут откладывать дольше), только при сети и только пока на экране есть виджет погоды; плюс разово при добавлении виджета и смене города. Источник — только наш сервер: `NexaApiSource` → `<api_base>/api/weather?lat=…&lon=…` (координаты города, выбранного в NEXA, до 0,1°; не выбран — `?city=kazan`; `WidgetStore.weatherQuery`) (интерфейс `WeatherSource`; напрямую к Gismeteo/Open-Meteo виджет не ходит). В `WeatherData` — cond, текст источника, мин/макс, `source`, `stale`, подпись источника. Внизу виджета — строка источника `weather_attr` («По данным Gismeteo» / «Данные: Open-Meteo»): нажатие открывает сайт источника во внешнем браузере (`Widgets.openSource`, только gismeteo.ru / open-meteo.com), нажатие на остальной виджет — приложение. Без сети — последняя удачная погода со временем («· сохранённые», если сервер отдал устаревшие). Старый формат (с кодом WMO) не читается — виджет загрузит заново.
  - Оформление: `widget_bg` (панель NEXA, обводка 1dp, без скруглений — но лаунчеры Android 12+ скругляют углы виджетов сами), уголок-складка `widget_fold` (две плоские грани), свои значки `ic_widget_*`. Цвета — `values/widget_colors.xml` и `values-night/widget_colors.xml` (тема системы). Тексты — `values/widget_strings.xml`; превью в списке виджетов — `widget_*_preview` (Android 12+) и векторы `widget_preview_*` (старее).
  - `am force-stop` отменяет нажатия на виджеты до их следующего обновления — так ведёт себя Android, при обычном закрытии приложения всё работает.
- Gradle в `android/` обновлён до 9.1: Android Studio идёт с Java 25, со старым Gradle сборка падает.

## Аккаунты (Supabase)

- Вход только по почте, кодом из письма, без паролей. Устройства и чаты к аккаунту пока не привязаны — живут в браузере, как раньше.
- Клиент — `src/lib/supabase.js`. Переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` (публичный ключ `sb_publishable_…`) лежат в `.env.local`, образец без значений — `.env.example`. Нет переменных — `supabase = null`: приложение работает как раньше, экрана входа нет, а «Войти» в Настройках говорит, что аккаунты недоступны.
- Разрешённые почты — `src/lib/allowedEmailDomains.js`: российские сервисы плюс любые домены в зонах .ru, .su, .рф. Тот же список на сервере — триггер в `supabase/restrict-email-domains.sql` (вставляется вручную в Supabase SQL Editor). Меняешь список — меняй в обоих местах.
- Логика — `src/lib/auth.js`: `useAuth` (кто вошёл, через `onAuthStateChange`), выход, тексты ошибок. Экраны — `src/screens/auth.jsx`: `AuthPanel` (почта → код 6–8 цифр, повторная отправка через 60 с, ошибки — `authErrorText`), `AuthGate` (экран первого запуска, макет 2026-10: фон — рендер устройств `public/art/gate-dark.webp` / `gate-light.webp` под тему, «стеклянная» карточка справа (телефон — шторка снизу); шаг 1 — знак NEXA, описание, «Войти» и круглая кнопка QR; шаг 2 — «Вход в NEXA»: `AuthPanel variant="gate"` (почта → код, «Войти по QR»); Esc / «Назад» — к шагу 1, на шаге 1 Android сворачивает. Гостевого входа на нём нет — решение автора; цвета карточки — токены `C.gate*`, внутри карточки переопределены `--text`, `--muted`, `--border`…), `AuthModal` (окно входа из Настроек), `AccountSettings` (группа «Аккаунт»).
- Гостевой режим — `nexa-guest` в localStorage (новым людям без входа не попасть: на экране первого запуска гостевого входа нет; остаётся у тех, кто уже гость). После выхода из аккаунта (кнопкой или когда сеанс завершили с другого устройства) снова показывается экран входа `AuthGate` — гостем после выхода не остаются (`nexa-guest` снимается). Сессию хранит сам Supabase (ключи `sb-…`), руками токены не писать.
- Выход — только на этом устройстве (`signOut({ scope: "local" })`), работает и без интернета.
- Демо-режима нет (убран по решению автора): ни у гостя, ни у аккаунта нет выдуманных устройств, файлов, вложенных папок, мастера «демо-устройство» и выдуманных переключателей устройства. Папки — только основные из `FOLDERS` (без `parent`) и созданные человеком. В списке устройств — только `real` (по коду/QR) и `bt` (пометки в `state`; фильтр после подстановки состояния) — старые выдуманные записи в данных остаются, но не показываются. Гость: «Добавить устройство» → окно входа с подсказкой (подключать можно только с аккаунтом). У аккаунта своё хранилище в браузере — ключи с id пользователя (`nexa-devices@<id>`, `nexa-files@<id>`). `useSharedState` умеет менять ключ на ходу. Выдуманные данные не добавлять.
- Уведомления — общие для аккаунта: `useAccountSettings` (`src/lib/accountSettings.js`), хранятся в профиле Supabase `user_metadata.nexa_settings = { notes: { files: true, … }, at }` (таблица и миграция не нужны; `auth.updateUser` / `auth.getUser`). Локально — `nexa-note-prefs` и время правки `nexa-settings-at@<uid>`. Сверка: при входе, возвращении в NEXA (не чаще раза в 30 с), возврате связи и по сигналу `sync.changed { table: "settings" }` (после отправки) — новее облако → берём, новее здесь → отправляем; без сети правка ждёт. Системные уведомления (разрешение) — у каждого устройства свои.

## Синхронизация с облаком (устройства и чаты)

- Таблицы — `supabase/sync-tables.sql` (вставляется вручную в Supabase SQL Editor):
  - `devices`: id uuid, user_id (по умолчанию auth.uid()), name, type (phone, laptop, tablet, watch, buds, tv), state jsonb (заряд, память, в сети ли, переключатели), created_at, updated_at;
  - `chats`: id uuid, user_id, title, messages jsonb, pinned boolean (миграция `supabase/chats-pinned.sql`, вставляется вручную), created_at, updated_at;
  - updated_at ставит триггер; RLS — только свои строки и только для authenticated, anon без доступа; индексы по user_id.
- Модуль `src/lib/sync.js`: хук `useCloudList` (одна таблица), `mergeLists` (сводка), `deleteAllMine` («Удалить мои данные»), `newId` (uuid). Гость — хук ничего не делает, всё как раньше.
- Данные всегда живут локально (`nexa-devices@id`, `nexa-chats@id`), облако — копия. При входе и при возвращении связи берём облако и сводим с локальным; удалённое без связи помнится в `nexa-sync@id` и удаляется в облаке позже. Изменения уходят в облако через ~1 с после последней правки.
- Подтверждённые версии — `ver` в `nexa-sync@id`: id → [updatedAt здесь, updated_at из облака] (upsert делается с `.select("id, updated_at")`). По ним `pendingCount` (сколько изменений ещё не подтверждено облаком; переживает перезапуск) и конфликты в `mergeLists`: менялось только здесь → отправляем; только там → берём облако; в обоих местах → `rows.resolve` (диалоги: объединяем сообщения без повторов, `CHAT_ROWS.resolve`) или более новая версия; удалили здесь, а там изменили → удаление отменено; удалили там, а здесь изменили → оставляем и отправляем. Без `ver` (старые данные) — прежнее «кто новее». Решённые конфликты → `onConflict` → уведомление «Конфликт: …» (`conflictNote` в NexaApp, больше двух — одно общее + записи в центре уведомлений). Правки, сделанные пока шла сводка, не затираются (`keepEdits`).
- Повторы: `syncErrorKind` — offline (ждём событие «online»), network/server (сами повторяем через `RETRY_DELAYS_MS` 3, 10, 30 с, дальше — только «Повторить» или возврат связи), auth/setup/denied (не повторяем; auth → «войдите заново»). Встроенные повторы клиента Supabase при чтении выключены (`.retry(false)`), иначе попытки перемножаются. Статус хука: `{ loading | ok, at | error, text, kind, nextAt, gaveUp, pending }`.
- Индикатор `SyncStatus` (внизу слева, на телефоне — над панелью; на ассистенте — строка в истории): «Нет сети · N изменений ждут отправки» (гость — «всё сохраняется на этом устройстве»), «Синхронизируем…», «Отправляем N…», ошибка с «повтор через N с» или «Повторить», «Сохранено в облаке» — 2,5 с только после подтверждения облака. Нажатие — окно `SyncDetails` («Связь и синхронизация»: каждая часть данных, очередь загрузок, удаления из облака, «Повторить сейчас», честная оговорка про фон). Сеть — `useOnline`.
- Без сети не копятся (кнопки выключены с причиной): Flow, «Найти», блокировка, отправка на устройство, подключение по коду, «Удалить мои данные». Сайт без сети не открывается (service worker нет); Android-приложение открывается с локальными данными.
- Чаты живут в NexaApp (`chats`; `setChats` ставит updatedAt), ассистент и поиск получают их пропсами. У гостя ключ `nexa-chats`, как раньше. Первый вход: если в облаке пусто, а гостевые чаты есть — копируются в облако один раз (`nexa-chats-migrated`), гостевые не удаляются.
- В облако идёт только то, что пользователь добавил сам; демо-устройств у аккаунта нет (см. «Аккаунты»). Новые id устройств и чатов — uuid.
- Состояние: на Главной заготовка строк, пока устройства грузятся; внизу тихая строка `SyncStatus` — «Загружаем данные аккаунта…» или «Нет связи, работаем локально» с кнопкой «Повторить». Тексты ошибок — `syncErrorText`.
- Мгновенно на других устройствах: после того как правки этого устройства ушли в облако (`onPushed` в `useCloudList`), по каналу связи уходит `sync.changed` `{ table: "devices" | "chats" }` — остальные сразу перечитывают эту таблицу (`refreshTableSoon`). Простая сводка при входе сигнала не шлёт — иначе устройства гоняли бы «обновись» по кругу.
- Файлы — см. «Хранилище файлов».
- Расписание («Сегодня») у аккаунта — `nexa-schedule@id` и таблица `schedule` (`supabase/schedule.sql`, вставляется вручную: day, time, title, place, RLS «только свои», до 2000 дел). `SCHEDULE_ROWS` в sync.js (в базе поле `day`, в приложении `date`). Пока таблицы нет — тихо работает локально, без строки «не настроено». Аккаунт впервые на устройстве — берёт дела, что уже были в этом браузере (раньше расписание было общим), и один раз отправляет их в облако (`nexa-schedule-migrated`). У гостя — `nexa-schedule`, только браузер.

## Хранилище файлов

- Сведения и байты раздельно. Сведения — `fileStore.added` в NexaApp (`{ id, name, cat, folder, device, mime, size, mb, path, addedAt, updatedAt }`), у вошедшего синхронизируются с таблицей `files` (папки — `file_folders`) через `useCloudList`. Байты: вошедший — закрытая корзина Supabase Storage `nexa-files`, путь `<user_id>/<id файла>`; гость — только IndexedDB этого браузера (в облако не уходит). Демо-файлов нет.
- Модуль `src/lib/files.js`: `uploadToCloud` (XHR — настоящий процент и отмена), `fileProblem` (до 50 МБ, без html/js/exe…), `safeFileName`, `fileUrl` / `useFileUrl` (память → IndexedDB → подписанная ссылка на 1 час), `removeFromCloud` + `flushTrash` (удаление без сети — повтор позже, `nexa-files-trash@<id>`), `cacheClearScope` (при выходе), `FILE_ROWS` / `FOLDER_ROWS`.
- Полноэкранный просмотр фото — `PhotoFullscreen` (перед `FileViewer`): нажатие на превью загруженного фото в окне файла («На весь экран»; у демо-файлов нет — нет содержимого). Листает все загруженные фото (`photos` в `FileViewer`, новые сначала, «N из M»): стрелки и ← → на компьютере, свайп на телефоне (на сенсорном экране стрелок нет — ловили палец). Приближение: двойное нажатие (2,5×), щипок, колёсико; приближенное двигается. Закрыть: крестик, Esc / «Назад» (слушает keydown в capture — закрывается только фото, окно файла остаётся), свайп вниз. Одно нажатие прячет панели. На сайте на компьютере ещё браузерный полноэкранный режим (Fullscreen API). Жесты — обычные addEventListener на сцене (не props React). Фон — токен `C.photoBg` (тёмный в обеих темах). Нет связи / не загрузилось — «Фото не загрузилось» и «Повторить».
- «Открыть» / «Скачать» — `openFileContent` (`src/ui/FileViewer.jsx`). Сайт: «Открыть» — вкладка открывается сразу по нажатию, адрес подставляется после (иначе Safari и Firefox блокируют); «Скачать» — ссылка с именем (у облака — подписанная ссылка с `download`). Приложение: встроенный браузер не скачивает и не открывает файлы — модуль `NexaFilesPlugin.java` (`nativeFile` в `src/native.js`): `save` — в «Загрузки» (Android 10+ через MediaStore, ниже — папка «Загрузки» приложения), `open` — в кэш и в другое приложение через FileProvider. Источник — подписанная ссылка облака (только https) или содержимое гостевого файла (base64); имя очищается от `/`, `..` и служебных символов.
- `FILE_SCOPE` — чьи файлы на экране (id аккаунта или "guest"); ставит NexaApp, читают `FileThumb` и `FileContentActions` («Открыть» / «Скачать» в окне файла; в приложении — всегда ссылка облака).
- Очередь загрузок без сети (только вошедший): нет сети или связь оборвалась посреди загрузки → `enqueueUpload` (содержимое — IndexedDB `<uid>:queue:<id>`, сведения — `nexa-upload-queue@<uid>`), строка «Ждёт отправки». Отправляет `runUploadQueue` в NexaApp: при входе/запуске, при возврате связи и по «Повторить»; перед каждым файлом сверяет, что сессия того же аккаунта. Повторы 5, 20, 60 с, дальше «Не загрузилось после N попыток — Повторить». id файла постоянный: ответ хранилища «уже есть» = загружено (без дублей). Выход стирает очередь вместе с остальными данными аккаунта. Отправка — только пока NEXA открыта.
- Файл появляется в списке только после того, как содержимое сохранено. Строки загрузки (`uploads`): процент, отмена, при ошибке — «Повторить» / «Убрать». Переименование меняет только сведения (в хранилище файл лежит по id). Удаление — сведения + объект Storage + копия IndexedDB. «Удалить мои данные» стирает и файлы.
- Объём в «Медиа и файлы» — только настоящие файлы: аккаунт — `cloudBytes()` (rpc `nexa_storage_used`, без ответа — сумма `size` загруженных) из `CLOUD_QUOTA_BYTES` (2 ГБ, как в правиле files-storage.sql) с полоской; гость — `localBytes` (что реально лежит в IndexedDB; файлы больше 25 МБ туда не попадают), лимита нет. Демо-файлы в объём не входят. Размеры — `formatBytes` (Б, КБ, МБ, ГБ; 1 КБ = 1024 Б, запятая).
- Supabase: `supabase/files-storage.sql` — таблицы `files`, `file_folders` (RLS, свои строки; `storage_path` обязан начинаться с `<user_id>/`), корзина `nexa-files` (закрытая, 50 МБ на файл), правила `storage.objects`: читать / класть / удалять только в своей папке, до 2 ГБ на аккаунт (`nexa_storage_used()`). Без этой миграции загрузка у вошедшего пишет «Облачное хранилище ещё не настроено».

## Погода (Gismeteo через наш сервер)

- Сайт, приложение и виджет берут погоду **только** с `api/weather.js`: `GET /api/weather?city=kazan` (Казань по названию — когда место не определено) или `GET /api/weather?lat=…&lon=…` (`WEATHER_API` в `src/lib/weather.js` = `API_BASE + /api/weather`). Напрямую к Gismeteo и к погоде Open-Meteo клиент не ходит.
- Документация Gismeteo — https://docs.gismeteo.net/v4/weather/ (страница рисуется скриптом; спецификация — `openapi.yaml` там же). Токен — заголовок `X-Gismeteo-Token`, переменная окружения `GISMETEO_TOKEN` (Vercel и `.env.local`): только в запросе сервера к Gismeteo; клиенту не отдаётся, в журнал не пишется, в код не вписывать.
- Один запрос на город: `https://api.gismeteo.net/v4/weather/forecast/h3?coordinates=<lat>,<lon>&days=14&locale=ru-RU` — в ответе и `current` (сейчас), и прогноз с шагом 3 часа на 14 дней (из него — мин/макс по дням по местному времени, `location.time_zone_offset`). Единицы по документации: °C, м/с, мм рт. ст., %.
- Место определяет устройство (вернули по просьбе автора): `useLocation` — геолокация браузера/приложения, дальше Яндекс `ymaps3.geolocation.getPosition()` (тот же скрипт, что у карты, ключ `VITE_YANDEX_MAPS_KEY`; по описанию Яндекса — браузер и/или IP), потом по IP (ipapi.co → ipwho.is → geojs.io); название по координатам — поиск Яндекса `ymaps3.search({ text: "долгота,широта", type: ["toponyms"], limit: 1 })` с ключом `VITE_YANDEX_SEARCH_KEY` (`setApikeys({ search })`; город — первая часть `description`, если там не регион, иначе `name` — `cityFromFeature`) → BigDataCloud → Nominatim → ближайший крупный город. Каждый шаг Яндекса — не дольше 7 с (`YANDEX_LOC_MS`), нет ключей — сразу прежние сервисы; вручную — поиск `CityPicker` (геокодер Open-Meteo, это не погода) и «Определять автоматически»; ручной город — `nexa-city`. Не определилось — Казань «по умолчанию». `weatherPlace(loc)` — что спросить у сервера: по умолчанию `city=kazan`, иначе координаты, **округлённые до 0,1° (~10 км)** — соседние запросы одного города попадают в общий кеш CDN и памяти. Сервер округляет так же сам (`placeOf`), неверные координаты → 400. По названию (`CITIES`) — только kazan и moscow. Название по координатам — своё (из `useLocation`), сервер отдаёт `location.name` Gismeteo.
- Ответ сервера (свой формат): `{ source: "gismeteo" | "openmeteo", stale, city: { id, name }, time, fetchedAt, now: { temp, feels, wind, humidity, pressure, cond, text }, days: [{ date, min, max, cond, text }], attribution: { text, url } }`. `cond` — свой код для значков NEXA (`WeatherGlyph`, `condLook`, `Widgets.weatherIcon`): sun | partly | cloud | overcast | rain | snow | sleet | storm | fog — считается по описанным полям Gismeteo (гроза, тип осадков, облачность 0–25 / 26–50 / 51–75 / 76–100 %). Код `icon_weather` в документации не расшифрован — не разбираем. Текст «сейчас» — `description` Gismeteo.
- Лимит бесплатного тарифа — 1000 запросов в месяц. Защита: `Cache-Control: public, s-maxage=3600, stale-while-revalidate=1800` (CDN Vercel); свежий ответ в памяти функции (час); одновременные запросы ждут уже идущий (`inFlight`); счётчик обращений к Gismeteo `gismeteo:month` (900 за 30 дней, `allow` из `api/_lib/rate-limit.js`) — дальше сразу резерв. Расчёт: каждое новое место (0,1°) — свой запрос не чаще раза в час; один город круглосуточно — ~720 в месяц, поэтому при многих городах счётчик (900) быстро переводит всех на Open-Meteo до конца 30 дней — это честно видно по подписи источника.
- Резерв: Gismeteo не ответил / 429 / нет токена / счётчик исчерпан → последний ответ из памяти функции с `stale: true` (кешируется 10 мин) → нет его — Open-Meteo (без ключа) с `source: "openmeteo"` и своей подписью → оба недоступны — 503 «Погода сейчас недоступна». Ошибки наружу без подробностей, в журнал — только код. Память функции живёт, пока экземпляр «тёплый» — после холодного старта резерв сразу Open-Meteo.
- Клиент: `useWeather(place)` — сразу последний сохранённый ответ (`nexa-weather:<место>` в localStorage, место — kazan или «55.8,49.1»), затем обновление (раз в 15 мин, «потяните», возврат сети). Строка под карточкой: «Обновлено в …», «Нет связи — данные на …» (сохранённые), «Источник недоступен — последние данные на …» (stale), ошибка с ↻. Нет данных совсем — «—» под вуалью, выдуманных цифр нет. Сводка ассистента пишет источник («По данным Gismeteo»).
- **Условие Gismeteo — брендирование**: рядом с любым показом погоды строка «По данным Gismeteo» с активной ссылкой https://www.gismeteo.ru (внешний браузер: `target="_blank" rel="noopener noreferrer"`) — `WeatherAttribution` (карточки «Погода», «Погода (завтра)», прогноз на 2 недели) и строка `weather_attr` в виджете Android. При резерве — подпись источника из ответа («Данные: Open-Meteo» → open-meteo.com), а не Gismeteo. Новый показ погоды — только с этой подписью.
- Проверка без Gismeteo: сервер с подменённым `fetch` (тест `weather_test.mjs`: запрос, заголовок, кеш, одновременные, 400, 429 → stale, 500 → Open-Meteo, 503, без токена, журнал) и сайт с настоящим `api/weather.js` (`weather_e2e.mjs`). `vercel dev` на компьютере автора не запускается.

## Связь устройств (Supabase Realtime)

- Модуль `src/lib/realtime.js`, хук `useDeviceLink(uid, { onText, onEvent })` в NexaApp. Отдельного блока «Передать на / История с» на экране устройства больше нет (убран по просьбе автора): текст и ссылки отправляются окном «Отправить в NEXA» (`FlowSendDialog` — быстрые действия, Настройки → Flow, «Поделиться» Android), история передач — в Настройках. Пришедшее показывается уведомлением.
- Канал: `nexa:<user_id>`, закрытый (`private: true`). Доступ — `supabase/realtime-policies.sql` (политики на `realtime.messages`: authenticated читает и пишет только в топик `nexa:<свой auth.uid()>`, расширения broadcast и presence). Гость к каналу не подключается.
- Устройство: `device_id` (uuid) создаётся один раз и лежит в localStorage `nexa-device-id`. Имя по умолчанию: «Приложение» (Capacitor), «Сайт на телефоне», «Сайт на компьютере».
- Presence (ключ — device_id): `{ device_id, name, kind: "web" | "app", platform: "desktop" | "mobile", joined_at }` (ISO-время входа). kind — по `Capacitor.isNativePlatform()`.
- Broadcast, событие `text.send`: `{ id (uuid), text (1–2000 символов), from_device, from_name, to_device (кому; null — всем), ts (мс) }`.
- Приём: пропускаем свои (from_device = свой), не нам (to_device ≠ свой), неверную форму, неизвестные события; с одного устройства — не чаще раза в 300 мс (так же ограничена отправка). Входящее — последние 20, localStorage `nexa-inbox@<user_id>`. Текст выводится только как текст; «Открыть» — только для http/https (`safeUrl`), `rel="noopener noreferrer"`.
- Статусы блока: «На связи», «Подключаемся…», «Нет связи», «Канал не настроен» (нет прав — не вставлены политики). При выходе из аккаунта и закрытии страницы (`pagehide`) — untrack и отписка от канала.
- Все события проверяются по схемам `SCHEMAS` в `src/lib/realtime.js`; неизвестные и неверные молча отбрасываются. К каждому отправитель добавляет `from_device`, `from_name`, `ts`. Отправка — через `link.emit(event, payload)`: пауза 300 мс соблюдается сама (очередь), приём с одного устройства — не чаще раза в 250 мс.

### Подключение устройства по коду / QR
- «Добавить устройство» у вошедшего открывает `PairModal`: код из 6 символов (`PAIR_ALPHABET`, без 0, O, 1, I, L), 2 минуты, таймер, QR на `<сайт>/?pair=КОД` (в приложении — https://nexa-link.ru), код текстом. Гость — сначала вход.
- Подключиться: открыть QR камерой (сайт заберёт `?pair=` и сразу уберёт из адреса; нет входа — сначала окно входа), в окне «Добавить устройство» → вкладка «У меня есть код» (`PairCodeForm`) или в приложении «Сканировать QR» (`scanQr` в `src/native.js`, Google Code Scanner из `@capacitor-mlkit/barcode-scanning`, разрешение на камеру не нужно; в AndroidManifest — meta-data `barcode_ui`). Отсканированное разбирает `parseNexaQr`: `?pair=` — подключение, `?login=` — вход по QR.
- `pair.claim` `{ code, device_id, name, kind, platform }` → выдавшее устройство сверяет код у себя (код только в памяти, `pairRef`, нигде не логировать): не истёк, не использован, не заблокирован. Ответ `pair.ok` `{ device_id, name }` или `pair.fail` `{ device_id, reason: wrong | expired | used | locked, left? }`. После 5 неверных — блок на минуту (и у выдавшего, и у вводящего — `nexa-pair-lock`). Верный код сразу недействителен, окно закрывается.
- Каждое устройство, где выполнен вход, само пишет себя в `devices` после первой сводки с облаком (эффект в NexaApp, `devicesLoaded`): тип по `thisDeviceKind` (смартфон / планшет → `tablet` / компьютер → `laptop`), вид сайт/приложение, `hw`; название, если его меняли, не трогает. Раньше в список попадал только тот, кто вводил код, а устройство, показавшее код, — никогда (из пары оставалось одно). Повторы одного `device_id` чистятся сами (оставляется самая ранняя запись, лишние удаляются и из облака). Поэтому «Новое устройство в аккаунте» приходит уже при входе на новом устройстве, а у выдавшего код часто вместо «Подключено новое устройство». В окне подключения — подсказка «проще всего войти в ту же почту».
- Подключённое устройство пишется в `devices` (через обычную синхронизацию): `type` phone/laptop, в `state` — `real: true, device_id, kind, platform`. Повторное подключение того же device_id не дублирует. Потом `devices.changed` `{}` — остальные перечитывают список из облака.
- Сайт и приложение одного телефона — одно устройство: «отпечаток телефона» `hw` (`phoneSignature` в realtime.js: экран, плотность пикселей, ядра, память, часовой пояс → короткая сводка FNV, только у телефонов) идёт в Presence и `pair.claim` и пишется в `state.hw` строки (своей и тех, кто в сети). `mergeSamePhone` склеивает записи с одинаковым hw в одну карточку: имя и id — приложения, `kind: "both"` («Сайт и приложение · телефон»), в сети — если в сети хоть одна, действия — туда, что в сети; `members` — все записи (удаление и переименование трогают все). Ограничение: два одинаковых телефона одной модели в одном аккаунте тоже склеятся.
- Реальное устройство: «в сети» — по Presence, «это устройство» — своё. Переименовать — карандаш у названия в шапке экрана устройства (`DeviceTitle`: поле того же размера, Enter / «Сохранить», Esc / «Отмена»; так же у Bluetooth-устройств), удалить — кнопка внизу. В серой плашке (`RealDeviceInfo` / `BtDeviceInfo`) — только сведения. Заряд и выдуманные переключатели у него не показываются.

### Найти устройство
- Кнопка «Найти» (`FindChip`) у реального устройства онлайн (не у себя) на карточке и на его экране. `find.ring` `{ target_device_id, id }` → у цели `FindOverlay` «Устройство ищут»: вибрация (`vibrate` в `src/native.js`: Haptics в приложении, `navigator.vibrate` на сайте), тихий сигнал Web Audio каждые 1,5 с (нет разрешения на звук — без звука), кнопка «Нашёл» (и Esc / «Назад»). Сам выключается через 60 с.
- `find.stop` `{ target_device_id, found }` → у отправителя «Нашлось» или «Не ответило». Волны на экране поиска неподвижны при `prefers-reduced-motion`.
- Сцен больше нет (убраны по решению автора).
- «Нашлось» уведомляет только того, кто искал (`findStateRef`), — `find.stop` видят все устройства аккаунта.
- Приложение закрыто / экран выключен — push через Firebase:
  - `findDevice` у устройства-приложения (`kind` app или both) дополнительно зовёт `api/push.js` (`pushFind`); если устройство не в сети по Presence, «Найти» всё равно доступно, но идёт только push.
  - Сервер `api/push.js`: проверяет вход (Bearer), берёт push-адрес только своего устройства из `push_tokens`, шлёт FCM HTTP v1 data `{ type: "find", id, from, target }`; JWT для Google подписывает сам (node:crypto), без лишних библиотек; лимит 10 в минуту на аккаунт; устаревший адрес удаляет. Без настроек — `{ sent: false, reason: "not_configured" }`, приложение пишет честно.
  - Нужны: таблица `supabase/push-tokens.sql` (вручную в SQL Editor; RLS «только свои», до 50 на аккаунт; «Удалить мои данные» стирает и её), переменная Vercel `FIREBASE_SERVICE_ACCOUNT` (JSON ключа сервисного аккаунта, целиком; плюс `SUPABASE_SERVICE_ROLE_KEY` и `SUPABASE_URL`), файл `android/app/google-services.json` (без него плагин google-services не подключается и Firebase не стартует — приложение работает как раньше).
  - Android: `NexaMessagingService.java` — NEXA на экране (`MainActivity.inForeground`) → ничего (сигнал пришёл по каналу); иначе уведомление «Устройство ищут» на канале `nexa-find` (звук будильника, вибрация, `FLAG_INSISTENT` — звонит, пока не откроют или не смахнут, `setTimeoutAfter` 60 с). Нажатие / «Нашёл» → `NexaPushPlugin` (событие `pushOpen`, при холодном запуске ждёт) → веб-часть отвечает `find.stop { found: true }`, как только есть связь. Push-адрес: `pushToken` → upsert в `push_tokens` (device_id, token), запоминается в `nexa-push-token@<uid>`.

### Где устройство (карта)
- Кнопка «Где устройство?» в `RealDeviceActions`. `locate.request { target_device_id, id }` → устройство отвечает `locate.reply { id, to_device, status: ok | off | denied | error, lat, lon, acc, at }` (схемы в `SCHEMAS`). Ждём 25 с, иначе «не ответило».
- Отвечает только если на нём включено «Поиск этого устройства» (Настройки → «Безопасность и приватность») (`nexa-locate@<uid>`, по умолчанию выкл.; при включении сразу спрашиваем разрешение геолокации). Место — один раз на запрос (`navigator.geolocation`, в приложении WebView сам просит разрешение Android; в манифесте ACCESS_COARSE/FINE_LOCATION). У отвечающего — уведомление «Местоположение показано «…»».
- Координаты только в памяти экрана (`locateState`) — не в облаке, не в истории, не в ленте.
- Карта — Яндекс Карты, JavaScript API v3 (`LocateMap` в `src/ui/LocateMap.jsx`, загрузчик — `src/lib/ymaps.js`, документация yandex.ru/dev/jsapi30). Leaflet и OpenStreetMap убраны.
  - Подключение: `loadYmaps()` сам добавляет `<script src="https://api-maps.yandex.ru/v3/?apikey=…&lang=ru_RU">` при первом показе карты, один раз на всё приложение, и ждёт `ymaps3.ready` (не дольше 15 с; не загрузилось — тег убирается, следующая попытка идёт заново). Ключ — `VITE_YANDEX_MAPS_KEY` (`.env.local` — сайт локально и сборка APK, `--mode android` его тоже читает; на Vercel — Environment Variables). Ключ в код и комментарии не вписывать.
  - Карта: `new YMap(контейнер, { location: { center: [долгота, широта], zoom }, theme, behaviors: ["drag", "pinchZoom", "dblClick"] })` — координаты у Яндекса в порядке [lon, lat]; масштаб как раньше: точность > 2 км — 12, > 300 м — 15, иначе 17; колёсико карту не масштабирует (прокручивается страница). Слои `YMapDefaultSchemeLayer` + `YMapDefaultFeaturesLayer` (без него маркер не виден). Круг точности — `YMapFeature` с многоугольником из 64 точек (готового круга в v3 нет), мятный 12% и обводка 1 px; точка устройства — `YMapMarker` со своим элементом (синяя, 14 px). «+ / −» — свои кнопки сверху справа (`map.update({ location: { zoom, duration } })`): готовые элементы управления Яндекса грузятся отдельным пакетом с чужого CDN.
  - Тема: `theme: "dark" | "light"` по `data-theme` у html; сменили тему NEXA — `map.update({ theme })` и новый цвет круга (MutationObserver).
  - Уход с экрана / новые координаты — `map.destroy()` и отписка.
  - Нет ключа / нет сети / API не ответил — заглушка `.nx-map-stub`: почему, координаты текстом и «Открыть в Яндекс Картах» (`yandexMapsUrl`: `https://yandex.ru/maps/?pt=lon,lat&z=17&l=map`); при ошибке ещё «Повторить», вернулась сеть — пробует сама.
  - Условия использования Яндекса: логотип, ссылки и копирайты на карте не скрывать и ничем не перекрывать (`copyrights` не выключать, свои кнопки — только сверху).
  - Ключ в кабинете разработчика Яндекса (developer.tech.yandex.ru): JS API v3 работает только с ключом, у которого заполнено «Ограничение по HTTP Referer» (вступает через ~15 минут). Разрешить: `nexaru-ecosystem.vercel.app` и `nexa-link.ru` (сайт), `localhost` (Android-приложение — страница в WebView открыта с `https://localhost`; и локальная разработка). CSP в проекте нет, у Android-приложения нет ограничений сетевых адресов (network_security_config), `INTERNET` разрешён — запросы к api-maps.yandex.ru не блокируются.
  - «Открыть в картах» под картой: приложение — `geo:` (откроется приложение карт телефона), сайт — Яндекс Карты. Работает, пока NEXA на том устройстве открыта или свёрнута.
  - OpenStreetMap в проекте остался только как Nominatim — название города для погоды по координатам (не карта).

### Bluetooth (часы, наушники)
- Только Android-приложение: `NexaBluetoothPlugin.java` — `status()`, `requestPermission()` (Android 12+ — «Устройства поблизости», BLUETOOTH_CONNECT; ниже — BLUETOOTH до SDK 30), `bonded()` — уже сопряжённые устройства: отпечаток адреса (sha-256, адрес наружу не уходит), имя, вид по классу Bluetooth (watch / buds / phone / laptop / tv / other), подключено ли и заряд (скрытые методы Android — где телефон позволяет), событие `changed`. Ничего не ищет и не подключает.
- Веб: `btStatus` / `btRequest` / `btBonded` / `onBtChange` в `src/native.js`; окно `BluetoothPicker` (кнопка `BtEntry` в окне подключения; на сайте — подпись «только в приложении»). Карточка — обычная запись `devices`, в state: `bt, bt_id, host, host_name, connected, battery, checkedAt`; подключено ли — знает только телефон-хозяин, он обновляет запись при изменении (раз в минуту и по событию). У Bluetooth-устройства нет демо-переключателей, «Подключить» и «Найти» — только статус, заряд (или «Нет данных») и `BtDeviceInfo` (название, с каким телефоном, честная оговорка).

### Сайт и приложение одного телефона
- Одна карточка (`mergeSamePhone`), а на экране — `PhoneParts`: «Приложение» и «Сайт» по отдельности, у каждого статус и заряд; если в сети оба — выбор «Действия сюда» (`partPick` в NexaApp, по умолчанию приложение). Быстрые действия идут в выбранную часть (`actTarget`).

### Реальные устройства: статус, быстрые действия, «Активность»
- Онлайн — только по Presence (`peerIds`), не по сохранённому флагу. Время последней активности — `state.seenAt` (мс) в строке `devices` (не путать со старым текстовым `lastSeen` демо-устройств). Своё устройство ставит `seenAt` при действиях человека и при уходе вкладки в фон — не чаще раза в минуту (`markSeen`); когда устройство пропало из Presence, его `seenAt` ставят те, кто это увидел. Подпись — `lastSeenText`: «Был в сети только что / 5 минут назад / вчера в 14:05».
- Быстрые действия — `RealDeviceActions` на экране реального устройства (не у себя): «Найти» (существующий `find.ring`), «Заблокировать экран», «Отправить файл», «Открыть на устройстве». Без связи или когда устройство не в сети — кнопки выключены, причина написана; у пропавшего устройства — «Подключить снова» (открывает существующий `PairModal`).
- `lock.on` `{ target_device_id, id }` → у цели `LockOverlay` «NEXA заблокирована» с «Разблокировать» и честной подписью «Это демонстрация…» (системный экран телефона не блокируется). `lock.off` `{ target_device_id }` → у отправителя «разблокировали».
- `file.send` `{ id, to_device, name, size, mime }` — файл уже загружен в корзину аккаунта (`uploadToCloud`, путь `<uid>/<id>`) и записан в `files`. Получатель строит путь сам из своего uid (чужому пути не верим), показывает уведомление с «Открыть» (подписанная ссылка). Не загрузилось — честная ошибка, без «отправлено».
- `link.open` `{ id, to_device, url }` — только http/https (`safeUrl` и при отправке, и при приёме); у получателя уведомление с кнопкой «Открыть», сама ссылка не открывается.
- Уведомление с кнопкой: `showToast({ …, action: { label, onClick }, duration })`.
- Лента «Активность»: `useSharedState("nexa-activity" + scope)`, последние 50, только этот браузер (на экране так и написано), вкладки одного браузера видят одно и то же. Записи `{ id, at, kind, title, text }`, kind: connect, disconnect, text, file, found, lock, link, sent. В ленту не пишем текст сообщений, ссылку целиком (только домен), коды и пути. Компактный `ActivityBlock` на Главной (у вошедшего), экран `ScreenActivity` («Очистить» — с подтверждением; «Назад» Android закрывает). Подключился / отключился — по смене Presence; первые 3 с после подключения к каналу не считаются.
- Настоящие сведения об устройстве — `src/lib/deviceInfo.js` (`useThisDeviceSys`): заряд и зарядка, тип сети, свободное/общее место. Приложение: `@capacitor/device` (getBatteryInfo), `@capacitor/network`, место — свой модуль `NexaDiskPlugin.java` (StatFs раздела данных, регистрируется в MainActivity; в @capacitor/device 8 полей diskFree/realDiskFree нет). Браузер: `navigator.getBattery()` (компьютер без батареи → «От сети»), `navigator.connection.type` + onLine; места на диске браузер не даёт. `navigator.storage.estimate()` для памяти устройства не использовать. Нет данных — «Нет данных», условных значений не подставлять, моделей и брендов не показывать (Смартфон / Планшет / Компьютер).
- Передача: поле `sys` в Presence (`link.shareSys`, не чаще раза в 30 с и только при изменении; приём — `cleanSys` в realtime.js). Последние сведения — `state.sys` строки устройства: пишет само устройство при уходе в фон и те, кто увидел, что оно пропало из Presence. Показ: «Это устройство» в Настройках (`ThisDeviceSettings`), карточка и экран реального устройства (Заряд, Память, Сеть, «Обновлено / Последние данные в …»).
- Сеть вернулась: если соединение с каналом не рвалось, `onOnline` в `realtime.js` сразу возвращает «На связи» и свежий список онлайн.

### NEXA Flow (общий буфер: текст и ссылки)
- Своей связи нет: тот же канал `nexa:<uid>`, событие `text.send` и хук `useDeviceLink`. Добавлено подтверждение `text.ack` `{ id, to_device, status: ok | off }`: получатель отвечает на адресное сообщение; `off` — у него Flow выключен (сообщение не принимается).
- Статусы отправленного (`sent` в хуке, localStorage `nexa-flow-sent@<uid>`, последние 20): sending → sent (сервер принял) → delivered (ack) / off / unconfirmed (нет ack 8 с; после перезагрузки страницы незавершённые тоже становятся unconfirmed) / error. Подписи — `FLOW_STATUS` в App.jsx.
- Дубли и петли: принятые id помнятся в `seenIds` (ref) — повтор не попадает во входящие, не даёт уведомления и автокопирования; ack не порождает ответов; своё не принимаем (from_device).
- Чувствительное — `isSensitive` в realtime.js (пароль/токен:…, ключи, JWT, PEM, «случайные» слова с цифрами и разным регистром): передаётся, но в историю пишется `text: null, sensitive: true` (`forStorage`), на экране «Скрыто», в уведомлении текста нет.
- Настройки — `nexa-flow@<uid>` `{ on }` (`FlowSettings` в Настройках: включить, «Отправить в NEXA», «Очистить историю»). Автокопирования нет (переключатель убран по решению автора; старое `autoCopy` в хранилище игнорируется): полученное копируют кнопкой «Копировать» во всплывающем. Буфер устройства сам не читается никогда: только кнопкой «Вставить скопированное» (`clipboardRead`).
- Буфер обмена — `clipboardRead` / `clipboardWrite` в `src/native.js`: приложение — `@capacitor/clipboard`, сайт — `navigator.clipboard` (нужен https и разрешение браузера). Будущий Windows-клиент — подключить сюда же.
- Окно «Отправить в NEXA» — `FlowSendDialog` (выбор устройства онлайн, причины, почему нельзя). Android: «Поделиться» → «Отправить в NEXA» — `NexaSharePlugin.java` (ACTION_SEND text/plain, событие `sharedText`, при холодном запуске ждёт подписчика) → `onSharedText` → то же окно; само ничего не отправляет. На iPhone (сайт) такого пункта нет.
- История передач — в окне и Настройках (`flowHistory`, `FlowItem`); на экране устройства её больше нет.

### Продолжение работы на другом устройстве (Continuity)
- Логика — `src/lib/continuity.js` (сроки, стадии, тексты причин), окно отправителя `ContinueDialog` и карточка получателя `ContinueOffer` — `src/ui/continuity.jsx`, ход — NexaApp (`startContinue`, `onContOffer`, `acceptContinue`…). Своей связи нет: канал `nexa:<uid>` и события `continue.*` (схемы в `SCHEMAS`).
- Что можно продолжить: диалог ассистента (меню «⋯» в истории → «Продолжить на устройстве…», быстрые действия → «Продолжить диалог на другом устройстве» — открытый сейчас первым) и файл из облака аккаунта (окно файла → «Продолжить на устройстве»). Ссылки и текст — прежний Flow / `link.open`, не дублируем.
- `continue.offer { id, to_device, kind: chat | file, ref, exp }` — только вид и номер объекта, без названия и содержимого; срок — 2 минуты (`CONT_TTL_MS`). Получатель принимает только от своего подключённого устройства (`real` в его списке), только адресованное ему и не просроченное; объект ищет в СВОЁМ аккаунте (диалог — `chats`, файл — `files` с `path`); нет — перечитывает таблицу из облака и через 3 с отвечает `missing`. Уже висит другое предложение — `busy`.
- `continue.reply { id, to_device, status }`: shown (карточка показана) → opened / declined («Не сейчас») / missing / expired / busy. Принимается только от того устройства, которому предлагали. `continue.cancel { id, to_device }` — отправитель передумал, карточка исчезает.
- Стадии у отправителя (`CONT_STAGE`): «Подключение…» (ждём канал до 10 с) → «Передача…» → «Передано — ждём, пока откроют» → «Открыто» / «Не удалось» с причиной (`CONT_FAIL`: нет связи, не ответило за 10 с, отключилось — по Presence, «Не сейчас», нет на том устройстве, время вышло, занято) и «Повторить»; пока ждём — «Отменить». Окно закрыли — итог всплывающим.
- Получатель ничего не открывает сам: карточка «Продолжить здесь?» (не модальная, над нижней панелью на телефоне, свайпы и быстрые действия не блокирует; Esc / «Назад» Android = «Не сейчас»), только по «Открыть» — диалог на экране ассистента (`chatOpenReq` → `openRequest` в `ScreenAssistant`) или окно файла. В «Активность» — «Продолжено на / с …».
- Ограничения: только внутри NEXA (не управляем окнами и приложениями системы); оба устройства должны быть открыты и в сети; диалог/файл должен успеть синхронизироваться (иначе честное «пока нет — повторите через минуту»); гостевые файлы (только в браузере) не продолжаются.

### Вход по QR (как в Телеграме)
- Новое устройство: экран входа → «Войти по QR с телефона» (`QrLoginView`): QR на `<сайт>/?login=КОД` и код из 6 символов, 2 минуты. Раз в 2 с спрашивает сервер «разрешили?»; получив одноразовый пропуск, входит им (`supabase.auth.verifyOtp({ token_hash, type: "magiclink" })`). Письмо не отправляется.
- Вошедшее устройство: Настройки → «Аккаунт» → «Войти на другом устройстве» (`ApproveLoginModal`): в приложении «Сканировать QR», везде — ввод кода. Сначала показывает, что за устройство просит («Разрешить вход?»), потом «Разрешить». Неверных кодов — не больше 5 в минуту (`nexa-approve-lock`). Ссылка `?login=КОД`, открытая камерой там, где уже вошли, сразу открывает это окно.
- Сервер — `api/qr-login.js` (действия start, poll, peek, approve; CORS как у `api/chat.js`). Пропуск — `auth.admin.generateLink({ type: "magiclink" })`, отдаётся один раз. Секрет нового устройства хранится только как sha256. Коды, секреты и пропуски не логировать.
- Таблица `qr_logins` — `supabase/qr-login.sql`: RLS включена без правил, доступ только у сервера.
- В Vercel нужны переменные: `SUPABASE_SERVICE_ROLE_KEY` (секретный, только на сервере) и `SUPABASE_URL` (или берётся `VITE_SUPABASE_URL`). Без них «Войти по QR» пишет, что вход по QR недоступен.

## Память ассистента

- Только то, что человек сам попросил запомнить. Модель в память не пишет и выводов о человеке не делает. Логика — `src/lib/memory.js`, хранение и действия — NexaApp (`memory`, `memoryApi`: add, update, setAlways, remove, clear, restore), Настройки → «Память ассистента» — `MemorySettings` (`src/ui/memory.jsx`, `#nx-memory-settings`): включить/выключить, добавить вручную, правка, удаление, «Очистить всё» с подтверждением; в центре безопасности — строка со ссылкой туда (не копия).
- Хранение: гость — `nexa-memory` (только браузер; при входе в аккаунт молча не переносится), вошедший — `nexa-memory@<uid>` и таблица `memory` (`supabase/memory.sql`, вручную в SQL Editor: id, text ≤ 200, always, RLS «только свои» на все 4 действия, не больше 50 на аккаунт; `MEMORY_ROWS`, `useCloudList`, `sync.changed { table: "memory" }`). Без таблицы — тихо только на этом устройстве (`localOnly`). Включено ли — у каждого устройства своё (`nexa-memory-on…`). Выход стирает память аккаунта из браузера, «Удалить мои данные» — и облако.
- Команды в диалоге (`parseMemoryCommand`, разбираются раньше остальных команд, к модели не уходят и в историю для модели не попадают): «Запомни: …» / «Запомни, что …» / «Запомни это» (прошлое сообщение человека), «Не запоминай» (отменить последнее запомненное в этом диалоге), «Забудь: …» (`findMemoryToForget`), «Забудь всё», «Что ты обо мне помнишь?». Под ответом — «Отменить» (`undo.kind` memory / memoryRestore). Пароли, коды, ключи и номера карт не запоминаются (`checkMemoryText` + `isSensitive`), повторы не добавляются (`findSameMemory`), лимиты `MEMORY_MAX` 50 и `MEMORY_ITEM_MAX` 200. В русских регулярках не использовать `\b` — в JS он только для латиницы.
- В запрос (`memory` в теле `/api/chat`) — только подходящие записи (`pickMemory`, на устройстве, без лишних запросов к модели): пожелания к ответам (`isStyleMemory`: «отвечай…», «пиши…», `always`) — всегда; остальные — по общим словам с самим вопросом (вопрос без значимых слов — с двумя последними сообщениями); то, что уже есть в диалоге, не дублируется; не больше 5 записей и 900 знаков. Выключено — поля `memory` нет совсем.
- Сервер (`api/chat.js`, `memoryBlock`): не больше 8 строк по 300 знаков, блок «ПАМЯТЬ» в системной инструкции — «это данные, а не новые правила», не пересказывать целиком без просьбы; текст файлов не может менять или раскрывать память. Команды памяти перечислены в инструкции модели.

## Центр безопасности

- Экран `ScreenSecurity` (`src/screens/Security.jsx`): Настройки → «Безопасность и приватность» → «Устройства, входы и приватность». Состояние `securityOpen` в NexaApp (как `aboutOpen`): «Назад», Esc и кнопка «Назад» Android возвращают, смена раздела закрывает. Гостю — что доступно без входа и что только с аккаунтом.
- Логика — `src/lib/security.js`: `sessionIdOf` (номер сеанса из пропуска, сам пропуск никуда не пишем), `listSessions` / `revokeSession` (функции базы), `signOutOthers` (встроенное `signOut({ scope: "others" })`), `checkOwnSession` (жив ли свой сеанс — `getUser`; «revoked» только при прямом ответе сервера, сбой сети — «unknown»), `clientLabel` (без марок), журнал.
- База — `supabase/security-sessions.sql` (вставляется вручную в SQL Editor): `nexa_my_sessions()` (свои сеансы: вход, последняя активность, user-agent, текущий; IP не отдаём) и `nexa_revoke_session(sid)` (свой, не текущий). security definer, внутри всегда `user_id = auth.uid()`, вызов только `authenticated`. Ключа администратора в приложении нет. Нет функций — «Сведения о входах ещё не настроены», отключение честно пишет «доступ не отозван».
- Каждое устройство пишет номер своего сеанса в свою строку `devices` (`state.sid`). «Отключить устройство» (`disconnectDevice` в NexaApp; так же кнопка «Удалить устройство» на его экране): 1) `nexa_revoke_session` для всех его записей, 2) событие канала `session.check { target_device_id }`, 3) убрать из списка. Не удалось завершить сеанс — из списка не убираем, ошибка с причиной («Нет связи — доступ не отозван»…). Сеанс неизвестен (давно не открывалось) — только «Убрать из списка» с предупреждением, что вход остался. Bluetooth — просто из списка (своего входа нет). Своё устройство — через «Выйти».
- Опасные действия (отключить, завершить сеанс, «Выйти везде») — подтверждение в строке, затем `runCritical`: 5 секунд и «Отменить» во всплывающем, только потом выполнение.
- Устройство само проверяет свой сеанс у сервера (`verifySession`): при входе, возвращении в NEXA (раз в минуту), возврате связи, раз в 10 минут на экране, по `session.check` и `devices.changed`. Сигналу не верим — только ответу сервера. Вышли не по кнопке «Выйти» (`takeManualSignOut` в auth.js) — стираем данные аккаунта на устройстве (`clearLocalAccountData`) и пишем «Сеанс этого устройства завершён».
- Ограничение (так и написано в интерфейсе): завершённый сеанс больше не продлевается, но выданный пропуск (JWT) живёт до своего срока — по умолчанию до часа; устройство в сети выходит сразу. Срок можно уменьшить в настройках Auth Supabase (JWT expiry).
- Журнал безопасности — `nexa-security@<uid>` (`useSharedState`, последние 50, только этот браузер, стирается при выходе): вход на этом устройстве (один раз на сеанс; давний вход — «Журнал начат…», время не выдумываем), подключено / отключено устройство, завершён сеанс, выход на других устройствах, разрешён вход по QR. Без кодов, токенов и адресов.
- Приватность в центре: «Поиск этого устройства» (переехал из Настроек, не дублируется), строка Flow со ссылкой на его настройки (`#nx-flow-settings`). Память ассистента — строкой со ссылкой на Настройки (`#nx-memory-settings`).

## Как устроен интерфейс

1. Объект `C` с токенами цветов. Значения — CSS-переменные (`var(--bg)` и т.п.).
2. Реальные цвета обеих тем задаются в блоке `<style>`: `:root[data-theme="dark"]` и `:root[data-theme="light"]`.
3. Тема хранится в localStorage под ключом `nexa-theme`. Переключается функцией `switchTheme`, это плавный переход через View Transitions.
4. Иконки в объекте `Icon`: SVG, нарисованные кодом, параметры `c` (цвет) и `s` (размер).
5. Экраны: `ScreenHome`, `ScreenToday`, `ScreenMedia`, `ScreenFiles`, `ScreenAssistant`, `ScreenSettings`. Экран устройства `DeviceScreen` открывается поверх текущего раздела (превью интерфейса — `DevicePreview`).
6. Мобильная версия собрана правилами `@media ${PHONE_MQ}` в том же блоке `<style>`: `PHONE_MQ` = ширина до 768 px ИЛИ сенсорный экран высотой до 500 px (телефон, повёрнутый горизонтально, остаётся мобильным), `DESKTOP_MQ` — всё остальное. В JS — те же константы (`useMediaQuery(PHONE_MQ)`). Новые правила для телефона писать через `${PHONE_MQ}`, не `max-width: 768px`. Нижняя панель — `MobileTabBar`: Ассистент, Сегодня, Главная (по центру, мятный значок крупнее, у подсветки мятная рамка), Медиа, Файлы (автор вернул прежний порядок после макета 2026-10). По макету 2026-10 (второй вариант) панель плавает: «таблетка» 62 px с отступами 16 px по бокам и 10 px снизу (над `--sab`), подсветка — скруглённая плашка; лёгкое размытие под панелью.
   - Свайпы между разделами (только телефон) — хук `useTabSwipe` перед NexaApp, порядок `SWIPE_ORDER` (как в нижней панели: assistant, today, home, media, files), без зацикливания. Касания только наблюдаются (passive), прокрутку и системные жесты не блокируют; мышь и колёсико не затронуты. Свайп: по горизонтали в 1,5 раза больше, чем по вертикали, и ≥ 60 px или быстрый флик (≥ 30 px, ≥ 0,5 px/мс, ≤ 300 мс). Не срабатывает: поля ввода, ползунки, QR (`data-no-swipe`), горизонтально прокручиваемые блоки, открытые окна / меню / уведомления / просмотр файла, шторка истории (у неё свой жест), 24 px у краёв (системный «Назад»), открытая клавиатура, экран устройства и «Активность», Настройки. Ассистент (первая вкладка): вправо — открыть историю (событие `nexa-open-history`), влево — Сегодня; при открытой истории влево по затемнению — закрыть (через Esc), разделы не переключаются. Во время жеста экран идёт за пальцем (`swipePlan`: смена раздела — 0,45 хода пальца, история или крайняя вкладка — 0,15, как пружина; не засчитано — мягко возвращается), засчитано — смена раздела через `navTransition` (см. ниже). У экранов на телефоне `touch-action: pan-y pinch-zoom`. При «уменьшении движения» — без движения. Новым элементам, где свайп мешает, давать `data-no-swipe`. Переход по меню (боковое на компьютере, нижняя панель на телефоне) и свайп — один путь `navTransition(dir, update)` в NexaApp: View Transitions — браузер держит снимок старого экрана, пока рисуется новый (без пропущенных кадров), двигается только `.ng-main-content` (`view-transition-name: nx-screen` при `html[data-nav-dir]`), меню и панель стоят; старый уезжает и тает 200 мс (48 px), новый въезжает с той же стороны 320 мс (64 px; `nx-vt-*`), направление — по месту в меню (`navDir`: `NAV` / `SWIPE_ORDER`), без направления — растворение. Прокрутка обнуляется сразу внутри перехода (`scrollTopNow`, сбрасывает и Lenis — `window.__nxLenis`), своё появление экрана (`ng-screen-in`) в этот раз выключено. Нижняя панель и строка синхронизации на время перехода — свои снимки (`nx-tabbar`, `nx-syncbar`) поверх экрана и без движения: иначе уезжающий экран наезжал на панель. Нет View Transitions — прежний въезд сбоку (`body[data-swipe]`, `nx-swipe-next` / `nx-swipe-prev`). `.ng-main-content { overflow-x: clip }` — въезжающий экран не даёт горизонтальной прокрутки. Новых анимаций смены раздела поверх этого не добавлять.
   - Ассистент на телефоне: шапка в одну строку — «ИИ — Ассистент» и маленькая версия рядом (`.nx-assistant-ver`), описание `.nx-assistant-subtitle` только на компьютере. Переписка (`.nx-chat-area`) — всё место между шапкой и полем; сообщения плотнее (`.nx-msg-col`, gap 14). Поле ввода — закреплённая область `.nx-chat-dock`: фон экрана на всю ширину и вниз до нижней панели, сверху переход 22 px от фона к прозрачному (не ловит нажатия; под ним запас в конце переписки). Нижний запас — CSS-переменная `--chat-bottom` у `.ng-assistant-inner`: плавающая панель (62 + 10 px) + `--sab` + 8 px = `calc(80px + var(--sab))`, при открытой клавиатуре 6 px. Свечение поля (`--input-glow`) на телефоне убрано, сине-мятная обводка осталась; подпись «ИИ может допускать ошибки» при клавиатуре скрыта. Поле растёт до ~6 строк, но не выше 30% видимой высоты (`fitInput`, пересчёт при смене размера) — на маленьком экране не выдавливает переписку.
   - Экранная клавиатура — один хук `useKeyboardViewport` в NexaApp: сразу (без задержек) ставит `--vvh` / `--vvt` (видимая область) и класс `kb-open` у body (поле в фокусе И экран ниже обычного больше чем на 120 px). При `kb-open` нижняя панель прячется мгновенно и убираются отступы под неё. Экран ассистента и `html`/`body` на нём — по `100%` / `--vvh`, не `100vh`. Список сообщений держится внизу при сжатии, только если человек и так был внизу. Новые компенсирующие отступы под клавиатуру не добавлять.
7. История чатов — в NexaApp (`chats`): у гостя localStorage `nexa-chats`, у аккаунта ещё и облако (см. «Синхронизация»).
   - Панель истории — `ChatHistory` (рядом с `ScreenAssistant`): компьютер — постоянная колонка слева; телефон (`useMediaQuery("(max-width: 768px)")`) — шторка в body на 85% ширины с затемнением `--scrim`, закрывается мимо, крестиком, свайпом влево, Esc/«Назад» (открытая — `role="dialog"`). Сверху «Новый диалог» и поиск (по названию и тексту), разделы Закреплено / Сегодня / Вчера / За 7 дней / За 30 дней / Раньше (`historyGroup` — по календарным дням), меню «⋯» (`role="menu"`): Закрепить, Переименовать, Удалить (с подтверждением). Внизу — строка синхронизации аккаунта (на экране ассистента общая `SyncStatus` не показывается) и аккаунт: почта или «Гость» → Настройки.
   - Потоковый ответ (`streamAnswer`) живёт вне истории: хранилище `live` (`liveSet`, `useLiveChatId`, `useLiveText`) и пузырь `LiveAnswer` — новый текст пачками раз в `STREAM_FLUSH_MS` (40 мс), перерисовывается только пузырь. Страницу закрывают или сворачивают посреди ответа — пришедшее сохраняется с пометкой (`partial: true`, `error: true`), готовый ответ его заменяет. Не возвращать запись в `setChats` на каждый кусок потока.

9a. Файлы в ассистенте (анализ содержимого). Скрепка у поля ввода → `QuickPanel` в роли выбора («С этого устройства…» + настоящие файлы из «Файлов»; неподходящие форматы видны, но не выбираются, с причиной; демо-файлы не предлагаются — у них нет содержимого). Подготовка — `src/lib/attach.js` (`prepareAttachment`), только в браузере, на сервер ничего не уходит до «Отправить»:
   - текст (TXT, MD, CSV, JSON, код; UTF-8, иначе Windows-1251) и DOCX / PPTX / ODT (текст из ZIP через `DecompressionStream`) → `{ kind: "text", text }`, до 100 тыс. знаков (`truncated`);
   - PDF и картинки (PNG, JPG, WEBP, HEIC; GIF/BMP и большие — в JPEG 2048 px) → base64 до `INLINE_MAX` 2,5 МБ (запрос на Vercel ≤ 4,5 МБ). Файл аккаунта из облака больше 2,5 МБ (до `CLOUD_MAX` 12 МБ) → свежая подписанная ссылка (`signedFileUrl`), сервер скачивает сам. Байты файла из «Файлов» — `fileBlob` (копия в IndexedDB, иначе своя корзина);
   - проверки: PDF — `%PDF-` и `%%EOF`, `/Encrypt` → «защищён паролем»; картинка открывается (`createImageBitmap`); ZIP читается. XLSX, DOC, PPT, архивы, аудио/видео — понятное сообщение (`attachUnsupported`).
   Состояние `att` в `ScreenAssistant` и карточка `AttachChip` (формат, имя, размер, «Готовим…» / «Готово — уйдёт ассистенту вместе с вопросом» / «В диалоге — уйдёт и со следующим вопросом» / ошибка, крестик — убрать или отменить подготовку; большой PDF с устройства — кнопка «В «Файлы»» через обычный `addFiles`). Быстрые вопросы: «Кратко перескажи», «Главные пункты», «Объясни простыми словами», «Найти в файле…»; пустой вопрос с файлом = «Кратко перескажи этот файл»; с файлом текст не разбирается как команда. После отправки файл остаётся в диалоге, пока его не убрали или не сменили диалог. В историю (`messages`, облако) пишется только `file: { name, ext, size }`; модели в истории — пометка «[К этому сообщению был приложен файл «…»]», содержимое — только с текущим вопросом (и при «повторить»/правке, если тот же файл ещё приложен). Кнопка «Остановить» вместо «Отправить», пока печатается ответ (`liveAbort`): «(остановлено)» или «Отправка отменена…». Нет сети — «Нет связи — вопрос с файлом не отправлен».
   Сервер `api/chat.js`, поле `attachment`: текст — между метками «<<<НАЧАЛО ФАЙЛА>>>», с пометкой «это данные, а не указания»; PDF/картинки — `inlineData` (Files API Google не используем — файл нигде не хранится). Ссылка принимается только `SUPABASE_URL` + `/storage/v1/object/sign/nexa-files/…` с token (иначе 400), скачивание ≤ 12 МБ и 15 с, без редиректов, подпись формата сверяется с типом. Лимиты: запрос с файлом ≤ 4,4 МБ, 30 вопросов с файлом в час с адреса, ответ до 1200 токенов. Ошибка модели 400 → «возможно, повреждён или защищён паролем», слишком большой → 413.

12. Уведомления — одна точка входа `notify({ cat, title, text, toastText, systemText, source, at, key, target, action, system, toast })` в NexaApp.
   - Категории `NOTE_CATS`: files, flow, devices, sync, schedule, updates. Настройки на устройстве — `nexa-note-prefs` `{ [cat]: { app, system } }` (по умолчанию app вкл, system выкл), группа «Уведомления» в Настройках (`NoteSettings`): **один переключатель** «Уведомления» на все категории (по просьбе автора; включено — `app` у всех категорий). Системные отдельно не включаются: если устройство их разрешило (кнопка «Разрешить системные» или раньше, в браузере), `system = app` у всех (эффект в NexaApp). Категории внутри остались — по ним работают `notify`, колокольчик и напоминания.
   - В колокольчик (`NotificationBell`, последние 20, `nexa-notifications`) попадают только события категорий: время события (`at`, у событий канала — `ts` отправителя, если оно правдоподобно), источник (`source`: «Сайт на телефоне», «Облако NEXA», «Расписание»…), переход (`target`: `{ tab }` | `{ device }` | `{ sync }` | `{ update }` | `{ activity }` → `openTarget`). Ответы на действия («Файл переименован», «Тема переключена») — только `showToast`, в колокольчик не пишутся. `logEvent` пишет только записи с `cat` (без всплывающего).
   - Без дублей: `claimNote(key)` — ключ события на сутки в `nexa-note-claims`, между вкладками под Web Locks. Ключи: `text:<id>`, `link:<id>`, `file-in:<id>:<ts>` (тот же сигнал дважды — одно; новая отправка того же файла — новое), `file-sent:<id>`, `newdev:<device_id>` (у выдавшего код и у остальных — один ключ), `sched:<id>:<дата>T<время>`, `update:<версия>`, `sync-fail|sync-ok:<uid>:<10-минутка>`. Лента «Активность» — свой журнал, но тоже без дублей (`logActivityOnce`).
   - Приватность: в колокольчике и системных уведомлениях нет текста сообщений Flow («Откройте устройство, чтобы посмотреть», у ссылки — только домен) и имён файлов в системном («Новый файл в «Файлах»»); сам текст — только во всплывающем на экране (чтобы скопировать).
   - Что уведомляет: файл отправлен / не отправлен / пришёл / загружен после сети; текст и ссылка с устройства; «Не удалось сохранить в облако» (только когда повторы кончились или сессия закончилась) и «Связь восстановлена» (только если перед этим был сбой или без сети ждали изменения, и облако всё подтвердило); новое устройство (подключено по коду; на других — появилось в подтверждённом облаком списке, `nexa-known-devices@<uid>`, первый раз запоминаем молча); «нашлось», «разблокировали»; дело через 15 минут (проверка раз в 30 с, пока NEXA открыта); «Вышла NEXA X» (приложение). Конфликты синхронизации — категория sync; у устройств — только конфликты удаления (служебные поля «был в сети», заряд не тревожат).
   - Системные: `src/native.js` — `systemNotifyKind` ("app" | "web" | "none"), `systemNotifyPermission`, `systemNotify`, `scheduleReminders`, `onSystemNoteOpen`. Показываем, когда NEXA не на экране (или «в приложении» выключено) и разрешение дано. Приложение: `@capacitor/local-notifications` (каналы `nexa-<cat>`, значок `res/drawable/ic_stat_nexa.xml`, разрешение POST_NOTIFICATIONS на Android 13+ — кнопка «Разрешить»; разрешили — системные включаются для всех категорий). Напоминания о делах (на 7 дней вперёд) ставит заранее Android — придут и при закрытом приложении, но могут опоздать (экономия заряда, телефон был выключен — тогда модуль покажет пропущенное после включения), поэтому в них «Скоро: …» и точное время, а не «через 15 мин»; в самой NEXA при этом только запись в колокольчик. Модуль плагина нельзя возвращать из async-функции (JS вызовет `.then` у плагина) — он отдаётся в обёртке `{ api }`. `getPending` модуля возвращает и уже показанные. Сайт на компьютере — Notification API, только пока вкладка открыта; сайт на телефоне — системных нет (без service worker), так и написано.
   - Сборка Android: модулю нужна Java 21 — в `android/settings.gradle` подключён `foojay-resolver-convention`, Gradle один раз скачивает JDK 21 в `~/.gradle/jdks`.

## Правила кода

- Комментарии в коде пиши на русском, коротко и понятно для новичка.
- Никаких hex-цветов прямо в разметке. Только `C.*`, а если нужен новый цвет, добавь токен в `C` и задай его в обеих темах.
- Не дописывай прозрачность к токенам хвостом вроде `${C.blue}80`: с CSS-переменными это ломается. Используй `color-mix(in srgb, ${C.blue} 50%, transparent)`.
- Любую правку проверяй в обеих темах и на мобильной ширине 390×844.
- Не переписывай файл целиком, если просят поправить одно место. Меняй точечно.
- Перед крупной переделкой предложи сначала сделать коммит.

## Визуальный язык

- Главный мотив — складка (fold): острые грани, геометрия.
- Углы скруглённые: поля ввода и мелкие плашки — 10px, средние карточки — 14–16px, крупные карточки и панели (настройки, баннер установки) — 18–20px, значки в строках — 16px. По макету 2026-10 крупнее: карточки устройств и ассистента на Главной — «таблетки» (999), «Активность» — 32, карточки экрана устройства — 40 (телефон 28), сцена устройства — 56 (телефон 32), шторка экрана обновления — 36. Прямые углы 4px больше не использовать. Обводки тонкие, 1px; у карточек нового макета — яркая `C.lineBright` (`--line-bright`, в обеих темах).
- Кнопки скруглённые: кнопки с текстом — «таблетки», кнопки-значки — круги. Это задаёт общее CSS-правило для классов `nx-ghost-btn`, `nx-primary`, `nx-icon-btn`, `nx-action` — новым кнопкам достаточно дать один из них. Скошенные чипсы пути (складка) остаются как есть.
- Свечение и заливки — только по макету 2026-10 (решение автора): точка статуса `.nx-status-dot` светится своим цветом; карточки-таблетки устройств залиты цветом статуса (зелёный/красный, слева гуще, к краю тает); у карточки ассистента — лёгкий сине-мятный градиент, на Главной компьютера ещё сине-мятное свечение вокруг (`.nx-ai-glow`); фон Главной — мягкое свечение `.nx-home-glow`; объёмная складка Главной — картинка со своим светом; на экране «Обновите NEXA» — мятный свет сверху и объёмная картинка со своим светом. В остальном — без свечения, размытия и мягких пастельных карточек; градиенты только там, где они несут смысл.
- Исключения для размытия (только они):
  - лёгкое размытие фона под окном «Добавить устройство», `backdrop-filter: blur(8px)`;
  - «стеклянная» карточка экрана первого запуска (`.nx-gate-card`, `blur(28px)`) — по макету автора;
  - плавающая нижняя панель телефона (`blur(14px)`) — по макету автора;
  - «вуаль» в карточке погоды: пока данные грузятся или не загрузились, значения и город размыты.
  - фон экрана ассистента (`AssistantSpectrum`): мягкое свечение и размытое цветовое поле разрешены только здесь, под всем содержимым экрана ассистента. На других экранах прежние правила.
- «Аура» нового диалога ассистента (`AssistantAura`) — крупная складка из полупрозрачных граней. Исключение из запрета на размытие: грани размыты (`filter: blur`, 34px, на телефоне 26px) в мягкое цветное поле, края растворяются маской (`mask-image`). Так же устроена маленькая аура за ответом (`ReplyAura`): появляется, пока ассистент думает, стоит за последним ответом и через ~2 секунды после него «испаряется». Анимируется только при появлении, за курсором/наклоном и при наборе текста.
- Анимация нужна только тогда, когда она что-то объясняет: появление, смену состояния, переход. Бесконечных декоративных анимаций не делать. Единственное постоянное движение — спектральный фон ассистента: он показывает состояние (ожидание / думает / отвечает).
- Спектральный фон ассистента — `src/lib/spectrum.js` (`runSpectrum`) и компонент `AssistantSpectrum` (первый слой в `.ng-assistant-wrapper`, содержимое над ним — `zIndex: 1`). Canvas 2D, не WebGL: пять радиальных градиентов в холсте ~120 точек по ширине, браузер растягивает его на весь экран — мягкость без фильтров. Цвета — из CSS-переменных темы (`--blue`, `--mint`, `--fold-cyan`, `--fold-deep`, `--blue-light`). Состояние читает каждый кадр из `live` (думает — ответа ещё нет, отвечает — текст растёт: импульс на каждую порцию), React не перерисовывается. Не чаще 30 кадров/с (мало заряда, экономия трафика или 2 ядра — 15), вкладка скрыта или ушли с экрана — не рисует, «уменьшение движения» — один неподвижный кадр. Середина приглушена в самом холсте (без CSS-масок). Светлая тема — слабее и медленнее. Нажатия и прокрутку не перехватывает (`pointer-events: none`).
- Складка Главной — `HomeFold` (вместо `FoldHero` на Главной): при первом открытии Главной за сессию раскрывается (~1,2 с, грани поворачиваются из общего сгиба, `sessionStorage` `nexa-fold-intro`), при росте числа устройств коротко «вздыхает» (~0,7 с). Анимируются только transform и opacity трёх SVG-граней (без теней и фильтров), в покое — та же картинка `fold.svg`; смена фаз — по таймеру (у скрытой второй раскладки Главной CSS-анимация не идёт). Параллакс — общий `useBackdropMotion` (курсор, наклон, прокрутка). Цвета граней — переменные `--fold-hf-*` в обеих темах. При «уменьшении движения» — сразу неподвижная картинка.
- Уважать `prefers-reduced-motion`.
- Цвета бренда: синий `#4A6FFF` (устройство) и мятный (связь, облако). Статусы: зелёный «онлайн», красный «не в сети».
- Шрифты: Space Grotesk для заголовков (класс `ng-display`), цифры через `NexaNumbers`.
- Ассистент везде называется «ИИ — Ассистент» (не «AI»).
- Картинки из макета — `public/art/` (WebP, прозрачный фон, обрезаны по содержимому): `device-phone.webp` (телефон на экране устройства), `update-stage.webp` (сцена «Обновите NEXA»), `home-fold.webp` (объёмная складка Главной на компьютере), `gate-dark.webp` / `gate-light.webp` (фон экрана входа, 2560 px; на наушниках пока виден чужой логотип — автор пришлёт рендер без него). Исходники PNG у автора; новые — так же: WebP ~1200–1600 px по длинной стороне.
- Экран «Обновите NEXA» (`ForceUpdateScreen`, макет 2026-10): непрозрачный, всегда тёмный (класс `.nx-force-update` подставляет цвета тёмной темы — картинка рисовалась под тёмный фон): сверху знак и NEXA, в середине сцена с тумбами, снизу шторка: «Обновите NEXA», текст, «Ваши данные останутся на месте» (щит), `UpdateActions` (кнопка, прогресс, ошибки — без изменений).
- Иконки свои, геометрические, а не скопированные системные.

## Экран «О системе»

- `ScreenAbout` (рядом с `ScreenActivity`): что такое NEXA, «Что умеет NEXA» (`ABOUT_FEATURES`), «Обновления» по версиям (`ABOUT_UPDATES`, новые сверху; текущая — мятная с меткой «сейчас»), «В планах» (`ABOUT_PLANS`, с оговоркой «планы, а не обещания»). Тексты — в этих списках, автор правит их там; **при выпуске новой версии добавлять её в `ABOUT_UPDATES` (`src/screens/About.jsx`)** (вместе с release-notes.md).
- Открывается: «Подробнее о системе →» внизу Главной (компьютер), кнопка «О системе» внизу мобильной Главной, Настройки → «Система» → «О системе». Состояние `aboutOpen` в NexaApp (как `activityOpen`): «Назад», Esc и кнопка «Назад» Android возвращают обратно, смена раздела закрывает.

## Контент интерфейса

- Никаких реальных брендов и названий продуктов в интерфейсе (iPhone, Windows и т.п.). Пиши «Смартфон», «Ноутбук», «Часы».
- Никаких сторонних или выдуманных брендов, кроме самой NEXA.
- Тексты интерфейса на русском, живым языком, без канцелярита.
- Настройки (`ScreenSettings`) — колонка до 920 px по центру свободного места (`.nx-settings`); поиска в самих Настройках нет — значок поиска в верхней строке.

## Безопасность

- API-ключи только в переменных окружения (`process.env`). Файлы `.env*` уже в `.gitignore`, их не коммитить и не выводить в чат.
- Не вставлять ключи в код и в комментарии.
- Проверка почты в React — только удобство. Защита данных — RLS в базе: `devices`, `chats` — только свои строки (`auth.uid() = user_id`), `qr_logins` и `api_rate_limits` — RLS без правил (только сервер). Новые таблицы с данными пользователя — сразу с RLS и правилами на все 4 действия.
- `supabase/security-hardening.sql`: счётчик запросов `nexa_rate_hit` (вызывает только service_role), ограничения размера (`devices.state` ≤ 16 КБ, `chats.messages` ≤ 1 МБ, имена/заголовки), не больше 200 устройств и 1000 диалогов на аккаунт, проверка почты и при её смене.
- Лимиты серверных функций — `api/_lib/rate-limit.js` (счётчик в базе, без service-ключа — в памяти): ассистент 15 вопросов в минуту и 300 в сутки с адреса, вопрос ≤ 4000 символов, история — последние 30, запрос ≤ 200 КБ; вход по QR — 10 новых кодов за 10 минут с адреса, 10 проверок кода в минуту и 40 в час на аккаунт. IP не храним — только sha256.
- В журналах (`console.error`) — только код ошибки, без текста запросов, кодов и токенов.
- Выход из аккаунта стирает из браузера ключи `nexa-…@<id>` и копии файлов аккаунта в IndexedDB (`clearLocalAccountData`); в облаке данные остаются.
- Проверка защиты — `supabase/security-test.sql` (часть 1 — два пользователя, всё откатывается; часть 2 — только чтение правил).
- В Supabase: Realtime → Settings → «Allow public access» выключить — иначе закрытость каналов не гарантирована.
- Отзыв доступа устройства — только через завершение его сеанса (`supabase/security-sessions.sql`, см. «Центр безопасности»). Удаление строки из `devices` доступ не отзывает.
