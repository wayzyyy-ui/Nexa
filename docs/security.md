## Центр безопасности

- Экран `ScreenSecurity` (`src/screens/Security.jsx`): Настройки → «Безопасность и приватность» → «Устройства, входы и приватность». Состояние `securityOpen` в NexaApp (как `aboutOpen`): «Назад», Esc и кнопка «Назад» Android возвращают, смена раздела закрывает. Гостю — что доступно без входа и что только с аккаунтом.
- Логика — `src/lib/security.js`: `sessionIdOf` (номер сеанса из пропуска, сам пропуск никуда не пишем), `listSessions` / `revokeSession` (функции базы), `signOutOthers` (встроенное `signOut({ scope: "others" })`), `checkOwnSession` (жив ли свой сеанс — `getUser`; «revoked» только при прямом ответе сервера, сбой сети — «unknown»), `clientLabel` (без марок), журнал.
- База — `supabase/security-sessions.sql` (вставляется вручную в SQL Editor): `nexa_my_sessions()` (свои сеансы: вход, последняя активность, user-agent, текущий; IP не отдаём) и `nexa_revoke_session(sid)` (свой, не текущий). security definer, внутри всегда `user_id = auth.uid()`, вызов только `authenticated`. Ключа администратора в приложении нет. Нет функций — «Сведения о входах ещё не настроены», отключение честно пишет «доступ не отозван».
- Каждое устройство пишет номер своего сеанса в свою строку `devices` (`state.sid`). «Отключить устройство» (`disconnectDevice` в NexaApp; так же кнопка «Удалить устройство» на его экране): 1) `nexa_revoke_session` для всех его записей, 2) событие канала `session.check { target_device_id }`, 3) убрать из списка. Не удалось завершить сеанс — из списка не убираем, ошибка с причиной («Нет связи — доступ не отозван»…). Сеанс неизвестен (давно не открывалось) — только «Убрать из списка» с предупреждением, что вход остался. Bluetooth — просто из списка (своего входа нет). Своё устройство — через «Выйти».
- Опасные действия (отключить, завершить сеанс, «Выйти везде») — подтверждение в строке, затем `runCritical`: 5 секунд и «Отменить» во всплывающем, только потом выполнение.
- Устройство само проверяет свой сеанс у сервера (`verifySession`): при входе, возвращении в NEXA (раз в минуту), возврате связи, раз в 10 минут на экране, по `session.check` и `devices.changed`. Сигналу не верим — только ответу сервера. Вышли не по кнопке «Выйти» (`takeManualSignOut` в auth.js) — стираем данные аккаунта на устройстве (`clearLocalAccountData`) и пишем «Сеанс этого устройства завершён».
- Ограничение (так и написано в интерфейсе): завершённый сеанс больше не продлевается, но выданный пропуск (JWT) живёт до своего срока — по умолчанию до часа; устройство в сети выходит сразу. Срок можно уменьшить в настройках Auth Supabase (JWT expiry).
- Журнал безопасности — `nexa-security@<uid>` (`useSharedState`, последние 50, только этот браузер, стирается при выходе): вход на этом устройстве (один раз на сеанс; давний вход — «Журнал начат…», время не выдумываем), подключено / отключено устройство, завершён сеанс, выход на других устройствах, разрешён вход по QR. Без кодов, токенов и адресов.
- Приватность в центре: «Поиск этого устройства» (переехал из Настроек, не дублируется), строка Flow со ссылкой на его настройки (`#nx-flow-settings`). Память ассистента — строкой со ссылкой на Настройки (`#nx-memory-settings`).

## Безопасность

- API-ключи только в переменных окружения (`process.env`). Файлы `.env*` уже в `.gitignore`, их не коммитить и не выводить в чат.
- Не вставлять ключи в код и в комментарии.
- Проверка почты в React — только удобство. Защита данных — RLS в базе: `devices`, `chats` — только свои строки (`auth.uid() = user_id`), `qr_logins` и `api_rate_limits` — RLS без правил (только сервер). Новые таблицы с данными пользователя — сразу с RLS и правилами на все 4 действия.
- `supabase/security-hardening.sql`: счётчик запросов `nexa_rate_hit` (вызывает только service_role), ограничения размера (`devices.state` ≤ 16 КБ, `chats.messages` ≤ 1 МБ, имена/заголовки), не больше 200 устройств и 1000 диалогов на аккаунт, проверка почты и при её смене.
- Лимиты серверных функций — `api/_lib/rate-limit.js` (счётчик в базе, без service-ключа — в памяти): ассистент 15 вопросов в минуту и 300 в сутки с адреса, вопрос ≤ 4000 символов, история — последние 30, запрос ≤ 200 КБ; вход по QR — 10 новых кодов за 10 минут с адреса, 10 проверок кода в минуту и 40 в час на аккаунт. IP не храним — только sha256. Правила проверяются одновременно (`allowEach` — ответ по каждому правилу, `allow` — все ли разрешают): раньше по очереди, у ассистента 2–3 захода в базу подряд до первых слов; ассистент проверяет минуту, сутки и файлы одним `allowEach`. Запасной счётчик в памяти при переполнении (5000) убирает истёкшие, потом старые незаблокированные — заблокированные последними (раньше стирался целиком, и лимиты обнулялись).
- Заголовки сайта (`vercel.json`, для всех адресов): `frame-ancestors 'none'` + `X-Frame-Options: DENY` (сайт нельзя встроить в чужую страницу), `nosniff`, `Referrer-Policy`. 
- CSP (2026-10-28) — пока `Content-Security-Policy-Report-Only`: браузер ничего не блокирует, а сообщает о нарушениях в `api/csp-report.js` (в журнал Vercel — только правило, источник без пути и раздел сайта; одно нарушение — одна строка на экземпляр, не больше 300). Разрешено: свой адрес, Supabase, Яндекс Карты и Метрика, сервисы определения города; встроенные скрипты index.html — только по отпечаткам sha256 (`'unsafe-inline'` для скриптов нет). Поменяли встроенный скрипт в index.html — пересчитать отпечаток в vercel.json, иначе упадёт `tests/csp.test.mjs`. Проверено в Chrome: сайт с этим заголовком — 0 нарушений, подложенный скрипт и чужой запрос — пойманы и отправлены в приёмник. Включать по-настоящему (`Content-Security-Policy`) — после нескольких дней без нарушений в журнале.
- В журналах (`console.error`) — только код ошибки, без текста запросов, кодов и токенов.
- Выход из аккаунта стирает из браузера ключи `nexa-…@<id>` и копии файлов аккаунта в IndexedDB (`clearLocalAccountData`); в облаке данные остаются.
- Проверка защиты — `supabase/security-test.sql` (часть 1 — два пользователя, всё откатывается; часть 2 — только чтение правил).
- Лимиты количества записей (memory 50, push_tokens 50) — триггер BEFORE INSERT, который Postgres вызывает и для upsert. Поэтому в функции лимита: чужая строка (`user_id` ≠ `auth.uid()`) — сразу дальше, отклонит RLS (не считаем и не блокируем чужой аккаунт); `pg_advisory_xact_lock` по аккаунту (одновременные добавления — по очереди); строка с тем же ключом уже есть (upsert станет обновлением) — лимит не мешает; иначе считаем. Функция — `security definer`, `set search_path = ''`, ошибка `23514`. Уже установленная база — `supabase/limits-fix.sql` (вручную в SQL Editor, повторный запуск безопасен). Новый лимит делать так же.
- Тест лимитов на локальном Postgres (к Supabase не подключается) — `supabase/tests/limits-test.mjs`: `cd supabase/tests && npm install`, потом `node limits-test.mjs new` (текущие файлы), `migrate` (база из старого коммита с данными + limits-fix.sql дважды), `old` (версия до исправления — ожидаются ✘). Зависимости теста — свой `package.json` в этой папке, в приложение не входят.
- В Supabase: Realtime → Settings → «Allow public access» выключить — иначе закрытость каналов не гарантирована.
- Отзыв доступа устройства — только через завершение его сеанса (`supabase/security-sessions.sql`, см. «Центр безопасности»). Удаление строки из `devices` доступ не отзывает.

## Политика конфиденциальности и «не дать базе уснуть» (2026-11-11)

- `public/privacy.html` — обычная страница сайта (`/privacy.html`, в sitemap): какие данные хранятся, у кого лежат, как удалить. Ссылки — на экране входа и внизу «О системе» (`API_BASE` + `/privacy.html`, в приложениях открывается во внешнем браузере). Добавили новый сервис, куда уходят данные, или новый вид данных — **обновить таблицу и списки на этой странице и дату версии**. Контакта автора на странице нет — для удаления самого аккаунта указано «свяжитесь с автором»; вписать почту / ссылку, когда автор решит.
- Cookie и счётчиков на сайте нет (Яндекс Метрика убрана 2026-11-11), баннер согласия не нужен. Появится счётчик или cookie — нужен баннер и правка политики.
- `api/keepalive.js` + Vercel Cron `0 3 * * *`: раз в день один лёгкий запрос к базе, чтобы бесплатный Supabase не заморозили после недели простоя. Лимит 6 в час, ничего не отдаёт кроме `{ ok }`.

## Проверка безопасности 2026-11-11

- Ассистент (`/api/chat`, и ИИ в заметках) отвечал любому в интернете — квоту Gemini мог тратить кто угодно (держали только лимиты с адреса). С 0.19.1 приложение шлёт ключ входа (`authHeaders` в `src/lib/supabase.js`), сервер проверяет его в `api/_lib/user.js` (`chatAllowed`, вместе с лимитами — без лишнего ожидания; удачная проверка помнится 5 минут). **Проверка включается переменной Vercel `CHAT_REQUIRE_AUTH=1`** — включить, когда приложение для ПК обновлено новым установщиком (у него веб-часть внутри установщика) и старые версии сайта / APK получили 0.19.1. До этого сервер работает как раньше. Тесты — `tests/chat-auth.test.mjs`.
- Окно «Разрешить вход?» (вход по QR): название устройства придумывает само просящее устройство — теперь «Называет себя «…»» и красное предупреждение «Код или ссылку вам кто-то прислал? Нажмите «Отмена»» (так крадут аккаунты: присылают `?login=КОД`).
- Проверено и в порядке: вход по QR (секрет только хешем, пропуск отдаётся один раз, перебор кодов ограничен на аккаунт), push (только свои устройства, текст буфера — из базы, не из запроса; ответ «Где устройство?» — по одноразовому ключу), вложения ассистента (ссылка только на свою корзину Supabase, без перенаправлений, предел размера и времени), ссылки в интерфейсе (`safeUrl`, `noopener`), вставки HTML в интерфейс нет.
- Осталось руками: Supabase → Realtime → «Allow public access» выключено; CSP перевести из Report-Only после нескольких дней без нарушений; `CHAT_REQUIRE_AUTH=1` (см. выше). Низкий риск, не правили: адрес ответа телефона на «Где устройство?» (`selfOrigin` в push.js) и адрес version.json в webpush.js берутся из заголовка Host — Vercel его не даёт подменить, но можно ограничить списком адресов сайта.
